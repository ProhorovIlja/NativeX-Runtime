# GTA VI native Windows/Linux — 23 November 2026 public upstream intake, license and performance evidence

**Scope:** One-time direct public GitHub source/README/license review for the user's objective: a native Windows x64 title host without CPU instruction emulation; Linux ELF where feasible or Windows PE under Proton as a separate compatibility path; modern graphics, storage, controllers and customizable engine-adjacent interfaces. This audit contains **no game executable, original assets, keys, dump/torrent URLs or DRM bypass** and is not a claim that GTA VI boots on a PC.

## What the public evidence currently proves

No independent GTA VI native Windows run, reproducible story-mode boot, physical GPU performance benchmark or official PC minimum specification is available from the inspected projects. The news about an alleged November Xbox package of around 209 GB, version 1.0.2.1, without its main executable is **an allegation** and the advertised November 23 EXE release is a *promise, not delivered evidence*. Public copyright status, encryption, authenticity and completeness are unresolved. Do not consume or redistribute untrusted executable downloads for this project. Do not promote cryptocurrency demands or imply that a file appearing in a torrent authenticates it.

An Xbox Series title's x86-64 code could in principle execute natively on compatible PC CPUs, but **that alone is not a PC port**. Xbox GDK/Game Core imports, ABI behavior, memory reservations/remaps, shader/resource formats, Xbox D3D12.X/XS graphics command differences, synchronization, assets, platform audio/input/network/save APIs and title initialization remain material obstacles. A native Windows host with translated console APIs does not imply an Xbox CPU emulator. Windows PE under Proton is not itself a native Linux ELF binary. Replacing some host C++ modules with Rust can improve memory safety or maintainability but does **not** rewrite or magically accelerate an unavailable proprietary game executable.

## The GPU and the low-end CPU are separate constraints

A claimed 30 FPS CPU minimum of `Ryzen 5 5600` is **not an official requirement**. A promised 60 FPS on all older processors is equally unsupported. A fixed simulation tick for an open world can be CPU-bound because of agent decisions, physics, collisions, scripting, animation, streaming and synchronization; lower render resolution, FSR/DLSS/XeSS and generated frames do **not** reduce the underlying per-tick CPU work. Conversely, real profiling may show room for better job scheduling, cache locality, bounded streaming, memory ownership, IO batching, LOD, culling and lower-quality presets on modest systems.

Treat 30/60/120 Hz as **target budgets**, not extrapolations:
- 30 Hz: frame interval approx. 33.33 ms.
- 60 Hz: approx. 16.67 ms.
- 120 Hz: approx. 8.33 ms.

Our native portable `Timeline` provides phases, and **PR #98** adds *Present-return cadence* and interval-deadline statistics; these are not physical displayed FPS. Before claiming CPU minimums, require *real game* simulation ticks, GPU timestamp/frame present statistics, p50/p95/p99, 1% lows, VRAM/RAM, IO stalls, and a reproducible scene/resolution/graphics preset on physical low/mid/high configurations. Native-rendered FPS must be reported separately from Frame Generation FPS. Keep memory and disk streaming bounded and avoid expensive compatibility shims on hot paths; measure rather than assume a language rewrite wins.

## Future integration order (technical priorities, not promises)

1. **Executable/ABI gate:** independently verified, lawfully accessible game build only; parse machine type, PE imports, TLS/unwind, memory allocations, GDK services, never execute unknown downloaded binaries in a privileged environment.
2. **Graphics boot gate:** D3D12.X/XS root signatures and pipeline state, command lists, shaders, wave32/64 parity, sparse memory/heap mapping, and first verified rendered frame, then stable Present.
3. **Resources gate:** synthetic RPF9 archive + TTPF metadata/tiling + BCPack bounded decode to BCn + GPU differential; video/audio containers; explicit type/format/license boundaries. Do not call a shader corpus validated by `spirv-val` equivalent to title draw correctness.
4. **Cross-platform gate:** native Windows first; Linux Proton for Windows PE as transitional support, native ELF/Vulkan is a distinct engineering path. Device/HID and save semantics differ by OS.
5. **Profiling gate:** physical hardware measurements before dynamic resolution, LOD/streaming/CPU presets, SR, latency and FG provider rollout. Large features (gameplay mods, phone UI, new animation/online systems, full language packs) need **verified title-specific code and assets** before claiming hook points or source-level control.

**No automatic scheduled or event-driven jobs/monitors, new CI schedules, background services, tracker subscriptions or external notifications were introduced.**
