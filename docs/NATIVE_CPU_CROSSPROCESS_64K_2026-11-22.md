# Native 64 KiB CPU shared-address aliasing between processes — Windows and Linux

Original source-built test `fixtures/native_shared_cpu64.cpp`, 2026-11-22. Both operating systems execute **real native kernel virtual memory APIs**, not an emulated instruction set or a simulated data container.

On **Windows x64**, the fixture creates a private named `CreateFileMappingW(INVALID_HANDLE_VALUE, PAGE_READWRITE)` pagefile-backed 64 KiB section, maps the exact same section into **two distinct CPU virtual addresses** with `MapViewOfFile`, writes and independently checks every byte, and launches a separate copy of its own binary with `CreateProcessW`. The child opens the same named section using `OpenFileMappingW`, maps its own view, verifies the original 65,536 bytes and writes an independent second deterministic pattern. The parent waits for the process and checks both of its existing views plus a newly mapped read-only view after unmapping the first.

On **Linux ELF**, the fixture creates a private `shm_open(O_CREAT|O_EXCL, mode 0600)` 64 KiB object, grows with `ftruncate`, maps it twice with `MAP_SHARED`, forks a separate OS process and explicitly opens and maps a *new shared-memory handle* in that child. The parent checks all 65,536 bytes through both mappings after the child finishes; it releases and re-maps the first view read-only, verifies again and unlinks the shared-memory object. A bounded 10-second watchdog forcibly cleans up its own stalled test child. Both OS paths clean up all handles and mappings.

What these fixtures prove: actual host CPU page sharing, virtual-address alias reads/writes, direct x86-64 native execution and correct interprocess visibility for this simple process-join ordering. They do **not** exercise Xbox console guest memory allocator/physical page tables, CPU↔GPU cache coherency, D3D12 tiled-resource views, cross-queue GPU sync, multi-threaded races, exotic huge pages, DirectStorage or GTA VI code. Windows and Linux are tested separately by existing CI. No persistent daemon, scheduled task, privileged device driver, external library, game file or network listener is created.

For contrast, [Windows WARP D3D12 64 KiB GPU tile aliasing](NATIVE_WIN_D3D12_TILE_ALIAS_2026-11-22.md) maps two virtual *GPU* pages to one backing GPU heap tile. This is a different address space and different API; success in both does **not** establish coherent CPU/GPU shared ownership. That will require properly synchronized resource state and actual physical GPU device/driver acceptance.
