# Xbox Series → native Windows/Linux: integration audit and actual platform acceptance (2026-11-22)

This is a source-backed, bounded research update to the project defined in the user-provided `Порт GTA 6.md`. The original plan explicitly requires **first** a working native Windows x64 single-player port, **second** a distinct Linux native ELF path, and **only then** cooperative gameplay and mission changes. No legitimate GTA VI Xbox Series X executable, assets, graphics traces or save-state format are available to this repository. All claims below distinguish **our independently passing CI fixtures** from **upstream author reports** and from **unimplemented game runtime**.

## New upstream investigation: concrete information, not implicit mergers

**Xbox2Windows** ([repository](https://github.com/R0Y00/Xbox2Windows), GitHub license metadata MIT):

- [PR #399](https://github.com/R0Y00/Xbox2Windows/pull/399), merged 2026-11-22: independent 5×7 **BC7 4×4-block** texture test checks placement of **35 blocks / 560 RGBA texels** into a **20×28 raster**; author reports a second `texture2ddecoder` oracle and negative test for power-of-two-only indexing. This is a useful template for strict rectangular texture layout checks once real assets may be legally inspected. Our project has **not** decoded any BC7 game texture.
- [PR #385](https://github.com/R0Y00/Xbox2Windows/pull/385), merged 2026-11-22: author reproduced Release `/O2 /NODEFAULTLIB` startup link failures when MSVC recognized fixed byte-copy loops and emitted unresolved `memcpy`. An inline x64 `__movsb` copy avoided CRT imports in those **upstream** builds. Our independent next source-built loader fixture is modeled as a regression test of the compiler/PE loader boundary, not copied source or a game ABI claim.
- Previous gfx10/RDNA2 and static recompilation tests are useful **test design inputs**, but source-side decoder coverage and unit tests cannot establish GTA VI rendering or real frame pacing.

**TomBox** ([repository](https://github.com/drycheetah84/TomBox), master `6ce59360e06b`, 2026-11-22): upstream author reports 68 passing Rust workspace tests, PSO-aware descriptor/resource bindings, RPF shader scanning and x86-64 compatibility fixes; a separate large shader archive translates 105,506/105,506 entries but that is **not rendered-correctness** or full title playability. The repository's own README calls it *early* and says the examined title reaches a menu but is not playable. As checked at this revision, GitHub did not advertise a recognized license and no top-level `LICENSE`/`COPYING` file was listed; **do not import its implementation into our MIT project without an explicit compatible grant**. Reviewing public algorithm descriptions is not equivalent to permission to copy code.

**XCL** ([commit `660f6dc2f0ee`](https://github.com/ivall/xcl/commit/660f6dc2f0eec8a14cf69c7cae0d8f1813da1fa1), GPL-2.0): the upstream author describes sparse GPU 4 GiB windows backed by real **64 KiB** host GPU tiles and changed-region synchronization. Their public result describes a title running for a short period with **black frames**, not a rendered playable scene. Our original D3D12 CPU/GPU alias tests **do not implement** that guest-memory subsystem and copy none of this GPL code.

**AnyXboxX** ([repository](https://github.com/LooperSalty/AnyXboxX), revision main `273bd9aec63f` observed 2026-11-22, GPL-3.0): [PR #78](https://github.com/LooperSalty/AnyXboxX/pull/78) changed its documentation metrics to quote CPU 100%, GPU 36% (521/1458), system functions 66% (876/1337), GDK runtime 38% (152/396) and D3D12.X 1/1 via TomBox DLL **without a title trial**. These are the **upstream project's own counters**, not a compatibility percentage for GTA VI, and they omit real graphics correctness. Our source-build gate still pins exact external revision `1a2e2e677c18e6ae4053eb84d4ff2395c538c108` in ephemeral CI, not its moving main; no GPL source is merged.

**Microsoft DirectStorage** ([PR #178](https://github.com/microsoft/DirectStorage/pull/178), 2026-11-19, MIT): its authors enabled a Zstd GPU execute-indirect workaround for a wider set of adapters based on reported correctness, performance and driver bugs. This is evidence that one-size-fits-all compressed-content pipelines can fail across drivers. Our verified Win32 IOCP async disk probe **is not DirectStorage** and we have not implemented title-specific ZstdGPU/BCPack/GDeflate decompression.

**Official upscaler SDKs**: [NVIDIA Streamline 2.14.16, DLSS 310.9.16, AMD FidelityFX SDK 2.4.0 and Intel XeSS 3.0.2](NATIVE_PC_GPU_SDK_GATES_2026-11-22.md) are public release references, not our code. DLSS 5 neural rendering should not be replaced with unlicensed binary injection or treated as an alias for DLSS Super Resolution. Real SDK selection requires engine color/depth/motion buffers, supported GPUs/drivers and independently measured picture quality, FPS, frame pacing and latency.

## Architecture decision: verify and adapt, do not concatenate repositories

1. **Windows-native platform foundation:** use original C++17/20 or Rust where ABI correctness and measured behavior justify it. The system code must execute genuine Windows x64 instructions with clean PE/GDK imports and host D3D12/DXGI semantics; separate handwritten adapters from source-derived vendor API wrappers. Switching everything to a fashionable language does **not** automatically reduce memory or CPU cost.
2. **Graphics correctness before modern effects:** apply independently source-verified GPU instruction translation, resource descriptors, BCn block tiling, shader binding and render-target semantics. Check test oracle against independent implementation and measured hardware on AMD/NVIDIA/Intel. Only after seeing real game frames optimize streaming, caches, VRAM, HDR, FSR, DLSS, XeSS and pacing.
3. **Disk/memory/media/audio:** compare actual IOCP vs DirectStorage on the title's verified asset format, GPU residency/budgets and SSD hardware. Build a real Windows Media Foundation/DXVA playback path and WASAPI stream once host capabilities and title cutscenes are available. The current PCM mixer and NV12 converter are separate standalone primitives, not a working media player.
4. **Input:** keep keyboard/mouse Raw Input and true GameInput/XInput devices, per-device state isolation, immutable frame snapshots and saved remapping profiles. Physical DualSense adaptive triggers/haptic feedback, provider deduplication, Xbox controller-specific feedback and actual end-to-end latency remain hardware acceptance gates.
5. **Linux:** build an independently runnable ELF+Vulkan native path (already compute and raster pixel reference tests), not simply label a Windows PE under Proton as a native Linux port. Proton is an optional second compatibility deployment route, subject to its own measured behavior.
6. **Actual game validation:** after an authorized Xbox Series X build exists, inventory its true PE imports, GDK service tables, memory-page assumptions, RAGE asset files/shaders, save data, playable loading and campaign progression. **Only game-specific execution and observed frames can advance from `fixture-tested` to `game-tested`.**

No scheduled tasks, background checks, persistent network services, game piracy downloads, unlicensed repo merges or privileged device drivers were introduced in this research batch.
