# Read-only PE32+ AMD64 xdata UNWIND_INFO v1 inspection — 2026-11-22

The existing original C++17 `src/pe_intake.cpp` already inventories PE exception directory `RUNTIME_FUNCTION` records (begin/end/unwind RVA) and source-built Windows TLS. This change **extends read-only analysis of v1 `UNWIND_INFO` headers and a limited subset of the AMD64 basic unwind operation encodings**, without executing the PE, adding a loader, or replacing Windows SEH.

Each entry in the new `unwind_infos` JSON array reports the xdata RVA, version, flags, prolog bytes, code slots, `decoded_v1_basic_operations`, a nullable **basic stack-allocation byte summary**, whether it chains to another runtime function, and an optional language-specific handler RVA. The existing `runtime_functions` and all previous fields remain; `unwind_codes_decoded:false` and `unwind_codes_executed:false` explicitly mean **no full runtime unwinding or x64 stack restoration is performed**.

For **version 1 only**, the parser checks 4-byte header and code array mapped into a PE section, padded code slots and any additional handler/chained record before following them. It recognizes `UWOP_PUSH_NONVOL`, `UWOP_ALLOC_SMALL`, both `UWOP_ALLOC_LARGE` forms, `UWOP_SET_FPREG`, `UWOP_SAVE_NONVOL` and its FAR form, `UWOP_SAVE_XMM128` and FAR, and `UWOP_PUSH_MACHFRAME`. It rejects an unknown v1 opcode, malformed large-allocation extension, invalid flags, a prolog-offset violation, missing/invalid handler RVAs or malformed chained `RUNTIME_FUNCTION` triples before emitting metadata. The `stack_allocation_bytes` field is a **basic arithmetic summary of explicitly encoded fixed stack adjustments** and is not a safe substitute for `RtlVirtualUnwind` or dynamic stack arithmetic.

**Version 2 and 3** may encode different epilog structures, new opcodes and payload extensions. They remain **explicitly opaque** (`decoded_v1_basic_operations:false`, allocation null), instead of being misrepresented as decoded version 1 or rejected merely for being newer. Those formats require separate first-party conformance tests against modern MSVC/Windows unwinder semantics before a safe decoder can be claimed.

## Source-built test cases

The synthetic PE test now contains two valid v1 records, aligned with its previously validated `.pdata`: a 40-byte `UWOP_ALLOC_SMALL` prolog and a second 16-byte stack allocation + 8-byte nonvolatile push with a handler RVA. It verifies exact JSON metadata, and tests corrupted version 0, excessive code slots, opcode beyond prolog, reserved v1 opcode, truncated large allocation, conflicting chained+handler flags, missing handler RVA and a deliberately newer v3 opaque record. The existing PE imports/exports/relocations/TLS positives and corruptions remain. CI compiles and runs the parser on Windows MSVC and Linux GCC; the Windows-native compiled DLL inventory is also checked.

Microsoft references: [x64 exception handling](https://learn.microsoft.com/en-us/cpp/build/exception-handling-x64) and [newer v3 unwind format](https://learn.microsoft.com/en-us/cpp/build/x64-unwind-information-v3). All implementation and synthetic data in this repository are independently authored; no proprietary Xbox files, source code from GPL projects, scheduled jobs or external binaries are added.

**Acceptance boundary:** this parser is for **ABI readiness discovery**, not game execution. The separate original [native Win64 registered-frame SEH fixture](NATIVE_WIN_DYNAMIC_SEH_UNWIND_2026-11-22.md) proves Windows can unwind through one independent synthetic function. Neither test establishes that a separately loaded Xbox executable has correct TLS/SEH imports, console GDK ABI, RDNA2 rendering, real game saves or physical GPU compatibility.
