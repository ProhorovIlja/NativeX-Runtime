# Independent Windows MSVC PE TLS and .pdata metadata plus runtime cross-gate (2026-11-22)

This test connects **two previously independently checked components**. The binary `scarlett_native_tls_fixture.dll` is compiled entirely from our original source under Windows/MSVC and then subjected to two separate acceptance paths:

1. **Read-only `pe_intake` metadata analysis:** `tests/check_compiled_pe_tls.py` invokes the portable PE32+ parser on the *actual compiled DLL*, checking that IMAGE_TLS_DIRECTORY64 describes a template of at least four bytes, a TLS index location, a non-empty callback table, and a non-empty sorted AMD64 `.pdata` function table. The parser **does not execute any DLL code**. It inspects independently generated real MSVC TLS/unwind data, not merely the synthetic binary used when the parser was developed. It then makes two disposable, deliberately corrupted copies: one with an out-of-range callback-table virtual address, the other with an invalid exception directory length. Both must fail parsing.
2. **Genuine Windows loader behavior:** the existing `native_win_pe_tls_callbacks_thread_lifecycle` CTest opens that same compiled DLL using OS `LoadLibraryEx`, observes TLS callback-before-`DllMain` ordering, independently initialized thread-local variables and clean thread/process detach. This native path runs real compiled code under Windows. Separately, the `native_win_seh_registered_x64_unwind` CTest validates actual `RtlAddFunctionTable` and native OS exception walking across an original synthetic x64 function.

The combined acceptance has **no imported game executable** and is not an AnyXboxX/GDK-loaded title. It does not prove that a manual PE mapper performs TLS callback order, registers .pdata or initializes console-specific GDK APIs. It instead checks that our read-only parser's interpretation of TLS/unwind metadata is consistent with the *same actual PE* that Windows' real OS loader executes, and that malicious malformed PE data is rejected.

Source implementation is `tests/check_compiled_pe_tls.py`; CMake registers `native_win_compiled_pe_tls_pdata_intake` on Windows x64. It requires only the existing CMake Windows SDK, MSVC, Python and source-built fixture; no physical gamepad, SSD, GPU or audio endpoint is needed. Linux continues to exercise the synthetic parser (without attempting to load PE code).

This closes an important **independent verification gap**, but does not complete Xbox Game Core loader compatibility. Further work: compare full Windows loader relocation/TLS/unwind semantics against specific lawfully obtained source-build GDK samples; avoid calling function pointer addresses from untrusted binaries. No proprietary code, external GPL source imports, scheduled jobs or persistent services were added.
